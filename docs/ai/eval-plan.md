# Evaluation plan

Status: draft for maintainer review · M1

## What good looks like

For an incident, the investigator names the true cause (or correctly says
there is none, or that it cannot tell), separates unrelated alerts, and
supports each claim with data it fetched. It never blames a healthy host
with confidence.

## Golden dataset

`sim/dataset.mjs`: 24 incidents on the simulated 19-host estate.

| Slice | Incidents | Why it exists |
| --- | --- | --- |
| Cause raises an alert | 14 | Sanity; reading alerts should nearly suffice |
| Cause raises no alert | 10 | The product's reason to exist: sub-threshold faults, missing triggers, stale metrics, resolved causes, unmonitored dependencies |
| No host tags | 4 | Estates with no recorded topology |
| Concurrent independent faults | 2 | Must report both |
| Benign alert | 1 | Must not invent an outage |
| Undeterminable | 1 | Must say so |

Slices overlap. The dataset is regenerated by `sim/replay.mjs`; answers
live only in `sim/scenarios.mjs`.

## Metrics

| Metric | Definition | Grader |
| --- | --- | --- |
| Cause accuracy | Verdict matches, and the true cause host (all of them, for independent faults) is named at medium or high confidence | Deterministic, from `truth` in the scenario |
| False blame | A host that is not a cause is named at high confidence | Deterministic |
| Unrelated separation | Older, unrelated alerts are listed as unrelated and not as causes | Deterministic |
| Evidence validity | Each evidence claim's numbers appear in the output of the query it cites | Deterministic check on recorded tool output |
| Mechanism | The explanation of *what* is wrong matches the scenario summary | Model grader with a written rubric, validated against a hand-labelled set before use |
| Cost and effort | Queries, tokens, cost and wall time per incident | Recorded |

Baselines reported next to every score: first-alert rule, and the same
model given only the alert list ("alerts-only").

## Pilot results (2026-11-16, one run each, Claude Sonnet 5.5)

| | Investigator | Alerts-only |
| --- | --- | --- |
| The 14 incidents new since M0 | 13 of 14 | 4 of 14 |
| All 24 | not run on all 24 | 12 of 24 |
| Cause raises no alert | 9 of 9 run | 0 of 10 |
| Cause raises an alert | 4 of 5 run | 12 of 14 |

The investigator was not rerun on the ten incidents that repeat M0
scenarios; it scored 10 of 10 on those in M0, on a different replay.
Scoring was by hand, by the agent that wrote the scenarios. Raw answers
and scores: `evals/golden/pilot/`.

The one miss: two concurrent faults (slow DNS and a bad deployment). The
investigator found the DNS fault and dismissed the deployment, misled by a
version metric sampled every five minutes.

## Thresholds for M3

Measured over three runs per incident, mean across runs.

| Metric | Threshold |
| --- | --- |
| Cause accuracy, all incidents | at least 85% |
| Cause accuracy, cause-raises-no-alert slice | at least 80% |
| Margin over alerts-only, all incidents | at least 25 points |
| False blame | zero incidents |
| Benign and undeterminable incidents | verdict correct in every run |
| Evidence validity | at least 95% of claims |
| Queries per incident | at most 30 |

These are set below the pilot numbers on purpose: the pilot is one run,
scored by the scenario author, on scenarios written by the same model
family. A threshold changes only by its own pull request with reasons.

## Known weaknesses to fix in M3

1. **Scale.** 19 hosts. Add an estate of several hundred hosts.
2. **Independent review.** Scenarios need review or authorship by someone
   who runs Zabbix in production.
3. **Variance.** One run per incident so far.
4. **Stale metrics.** Add scenarios built around slow-sampled items, since
   that caused both reasoning errors seen so far.
5. **Injection.** Add a red-team set: instructions planted in alert names,
   tags and item values. Zero tool misuse is required.
6. **Smaller and local models.** Not yet evaluated.
7. **Automated scorer.** Scores are hand-assigned; the deterministic graders
   above are to be written in M3, before any prompt work.

## Process

- `make eval` runs the suite and writes a report with baselines.
- CI runs a fast subset on any change to prompts, tools or the agent loop,
  and fails on a threshold breach or a regression against the stored
  baseline.
- Every miss in a pilot or in production becomes a scenario before the fix
  merges.
